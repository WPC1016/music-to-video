# 决策记录

只记"为什么这么选"，不记操作步骤。新的写最上面。

---

## 2026-10-21 · 采纳 ChatGPT 方案的状态机与审核点，但不改目录命名

**决定**：吸收「8 阶段状态机 + 4 个审核点 + 素材清单 + 分镜 JSON 完整 schema」；不采纳它的目录重命名（`projects/` `input/` `creative/` `assets/`）。

**原因**：方案的结构化思路是对的 —— 状态要机器可查、审核要留痕、素材要可追溯。但目录名只是同义词替换，改了等于把已跑通的东西推倒。`songs/` `source/` `concept/` `refs/` 在中文语境里更直白。

**代价**：和网上教程的目录对不齐。无所谓，规范在自己手里。

---

## 2026-10-21 · 素材清单用 type 字段分类，不建空目录

**决定**：`asset-manifest.json` 里用 `type`（style-board / character / background / keyframe / clip）区分，`refs/` 不按类型分子目录。

**原因**：多数歌是抽象/风景/图形，根本没有角色。建五个空目录，第四首歌就会出现"这个图该放哪"的犹豫。

**代价**：找图要靠 manifest 或文件名前缀。可接受。

---

## 2026-10-21 · Phase 1 不装 Remotion

**决定**：不执行 ChatGPT 方案的「阶段 0：跑通最小视频工程」。

**原因**：分镜没定就选引擎，等于瞎猜。画面要多复杂、要不要 3D、要不要粒子，这些决定引擎选型，而它们来自分镜。现在装 Remotion 是装一套闲置依赖。

**触发条件**：Step 5 分镜定稿后，按画面复杂度在 `canvas` / `hyperframes` / `remotion` 里选一个，那时再装。

**代价**：Phase 1 没有可跑的视频。靠参考图和分镜表判断，够用。

## 2026-10-21 · Phase 1 不做渲染

**决定**：先只做素材、分析、解读、概念、风格、分镜、参考图。`engines/` 保留但不动。

**原因**：每首歌风格差异大，渲染是"风格定死之后的实现问题"。风格没定就写渲染代码，等于把第一首歌的解法套给所有歌，后面每首都得推翻重来。

**代价**：暂时没有可视化的中间产物。靠参考图和分镜表判断，够用。

---

## 2026-10-21 · 提示词库放根目录 `prompts/`，每首歌复制使用

**决定**：五段提示词作为项目级资产，不放在 `songs/<歌>/` 里。

**原因**：提示词是"方法论"，会随做的歌越来越多而迭代；如果每首歌一份，改一次要改十处。歌目录里只放**跑出来的结果**。

**代价**：跑提示词时要跨目录复制。接受。

---

## 2026-10-21 · 每首歌强制 `00-风格定义.md`

**决定**：风格卡是必填项，且不许抄。

**原因**：这是同类项目最常见的死法 —— 第一首定了水墨风，第二首直接复用，最后十首歌长得一样。用文件强制"重写"这个动作。

**代价**：每首多花 10 分钟。值得。

## 2026-10-21 · skill 真身放 `.agents/skills/`，其余用 junction

**决定**：`.agents/skills/music-video/` 是唯一真身，`.claude` / `.workbuddy` / `.cursor` / `.zcode` 下都是 Windows junction。

**原因**：`npx skills add` 的默认落点就是 `.agents/skills/`，Codex 和 Cursor 原生读这里。其余工具用 junction 链过去，避免四份副本各自漂移。

**代价**：Git 不跟踪 junction，换机器要重跑 `npm run skills:link`。已写进文档。

## 2026-10-21 · 引擎以 canvas 为主，HyperFrames / Remotion 备选

**决定**：`song.json` 的 `engine` 默认 `canvas`。

**原因**：`../天地龙鳞` 已验证：1080p 205 秒，6 进程约 3 分钟，零 npm 依赖，画面完全可控。HyperFrames 官方 `music-to-video` skill 流程设计得好，但首次 `npx` 拉包慢；Remotion 适合批量同风格。

**代价**：所有绘制元件要自己写，没有模板生态。

**这条 Phase 2 再验证，现在不影响。**
